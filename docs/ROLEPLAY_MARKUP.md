# Roleplay markup

Roleplay is presentation inside an assistant response, like recipes. A response can contain ordinary Markdown, one or more `<roleplay>` scenes, and more Markdown afterward. `<roleplay_markup>` is accepted as an alias for either tag, and wrapper attributes are ignored; the skill teaches `<roleplay>`.

```xml
Here is the scene.
<roleplay>
  <narration>A truck passes outside.</narration>
  <character id="adelle" name="Adelle">
    <move via="foot">She crosses the muddy floor.</move>
    <action>She grabs the book.</action>
    <thought>Finally.</thought>
    <dialogue>Tell me you brought the car.</dialogue>
  </character>
  <character id="monica" name="Monica">
    <move via="car">She reverses toward the warehouse.</move>
    <dialogue>Get in.</dialogue>
  </character>
</roleplay>
```

`<say id="rook" name="Rook">Line.</say>` is optional shorthand for a single spoken line, taught for quick, snappy exchanges. It is placed where a character group can be (in the scene or a flashback), never inside one; a say inside an open group or beat closes them first, like a new character. `name` may be omitted once the ID has appeared in the scene; an unknown ID falls back to its capitalized form. Say lines render as compact exchange rows: the portrait beside the bubble and the name inside the first bubble, aligned with full groups. A row stays hidden until its first line has text. Consecutive say lines by the same speaker stack in one row, and a say directly after that speaker's full group joins it as dialogue, but a full group never folds into an exchange row, so a row cannot switch layouts mid-stream. Copy renders exchange rows as `Name: “Line.”`.

`flashback` can contain narration, character groups, and say lines. Character groups establish ownership without repeating actor attributes; back-to-back groups with the same ID render as one group. Background activity remains narration. `move` is a character's travel; `via` names the means in one free-form word. The model is never shown the icon list; `travelMode` in `src/lib/roleplay.ts` maps words, synonyms, and simple inflections to about 34 modes across ground, rail, water, air, space, fantasy, and mounts, so the vocabulary can grow without prompt changes. Ambiguous words (coach, gondola) and unknown means fall back to a generic route icon. Lucide lacks mounts, so `src/components/roleplay-travel-icons.ts` adds horse, unicorn, and UFO icons from Lucide Lab (ISC) plus custom dragon-wing and carriage icons on the same 24px grid. The earlier `<walk>` and `<drive>` tags still render as `move` with `via="foot"` and `via="car"`. Dialogue has no surrounding quotation marks or speaker label; its bubble provides the visual treatment, and inline emphasis is allowed. Other beats support Markdown. Unrecognized tags inside a scene remain readable text, never executable HTML.

`src/lib/roleplay.ts` splits scenes and parses a bounded tree. Messages without a wrapper skip parsing. Streaming holds possible opening/closing tag fragments until they can be classified. It does not wait for the complete scene or require it to start the response. Completed beats and partial prose render as they arrive, and only the beat still receiving tokens is rendered in streaming mode. Missing closing tags retain readable content in the scene; a new character implicitly closes an omitted previous character closing tag. Fenced, inline, indented, and escaped examples are not activated as scenes.

`RoleplayScene` provides the shared presentation used by live chat and the Persona editor's format preview. Actions, movement, thoughts, and flashbacks carry a gutter icon with a hover label; dialogue is a bubble. Character groups and the scene are labelled groups rather than landmarks or headings, and thoughts and dialogue carry visually hidden "Thinks"/"Says" prefixes for screen readers. Avatar sources come from a trusted application map keyed by character ID and passed by the caller, never model-written URLs or names. Unknown characters use initials. The Persona editor preview supplies an existing local portrait as a stand-in for its supporting character. Copy and read-aloud extract character names and prose instead of exposing the native tags or IDs, quoting dialogue and italicising actions, movement, and thoughts.

In Persona conversations, `Chat` derives the display identity from the thread's saved Persona metadata (`personaName`, `personaAvatarKind`, `personaAvatarValue`, written from the snapshot at creation) and supplies it through `RoleplayPersonaProvider`, so memoized messages update when the thread loads. Before thread creation, the selected Persona supplies the identity for an authored opening. Once the thread exists, the picker is never used as a fallback; this prevents an unrelated selection from changing an old conversation.

Only the exact, case-sensitive character ID `persona` binds to the saved Persona. Names never determine avatar ownership. The skill receives the saved name and instructs the model to use `id="persona"` exclusively for that Persona, with different stable IDs for supporting characters even when their names are identical. It spells out the exact opening tag with the saved name and names the name-derived ID to avoid (`id="seraphine"`), because weaker models otherwise copy the name-like IDs from the example. It also tells the model that the format replaces italic or asterisk stage directions from Persona instructions. The same character keeps its ID across groups, turns, and flashbacks. Without a Persona, the model is instructed not to use the reserved ID. A bound group displays the canonical saved name and uses `getPersonaAvatarSrc`, the same resolver as ordinary Persona avatars, for built-in assets and R2 references. The model voices the user's character only when the user delegates control, and then always as the reserved `id="user"`. That group keeps its in-story name (falling back to "You") and takes the signed-in user's OAuth profile image from `session.user.image`, supplied by `Chat` through `RoleplayUserImageProvider`. Shared views have no provider, so a public share never shows the owner's photo. Legacy markup without IDs still renders with initials; there is deliberately no name fallback. Public shared snapshots currently do not contain Persona identity, so they retain the initials fallback. No automatic portrait generation or per-thread supporting-character registry is implemented; supporting IDs are carried in conversation markup, not a separate database record.

The `roleplay` app skill has no executable tools. It can be preselected for opening roleplay requests, loaded on demand, or included in the base formatting prompt for models without function calling. Personas opt in with `roleplayFormat` (the "Rich Roleplay Format" switch in Persona settings; set on character built-ins). The flag is copied into the thread's Persona snapshot, so changing it affects new conversations only. Opted-in Personas preload the skill on every turn, independently of the opening classifier and automatic tool-selection setting. For other conversations, the last substantive assistant response on the selected conversation branch is inspected; a roleplay scene makes the skill a preload candidate. This restores the instructions without another `load_skill` call. User text and fenced examples do not activate continuation. Preloads stay within the existing context admission limit; opening selections are admitted first, so a roleplay preload cannot displace them. Existing opening-selection persistence still applies.

Run `bun run test tests/lib/roleplay.spec.ts tests/components/roleplay-rendering.spec.ts tests/backend/roleplay-skill.spec.ts` for parser, rendering, and continuation coverage. Live classifier cases are in `scripts/evals/opening-skills-cases.ts`; their probabilities have not been evaluated as part of the offline tests.
